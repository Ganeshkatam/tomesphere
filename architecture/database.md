# Database Architecture

## Purpose

This document defines TomeSphere's persistence architecture, data ownership, schema organization, security model, and database engineering standards.

The database is built on PostgreSQL (Supabase) and follows a domain-oriented schema with Row-Level Security (RLS), strict typing, and normalized relationships.

---

# Technology Stack

Database

- PostgreSQL

Platform

- Supabase

Authentication

- Supabase Auth

Authorization

- PostgreSQL Row-Level Security (RLS)

Storage

- Supabase Storage

Migration Tool

- Supabase CLI

---

# Database Philosophy

The database follows these principles:

1. Domain-oriented schema.
2. Normalized relationships.
3. Row-Level Security by default.
4. Strong referential integrity.
5. Database enforces invariants whenever possible.
6. Application owns business rules.

# Table Ownership

Each table has a single aggregate owner.

Example

```
books

↓

book_likes

↓

book_comments

↓

ratings

↓

reviews
```

Avoid tables shared across unrelated domains.

---

# Naming Conventions

Tables

Plural.

Examples

```
books

profiles

collections
```

Relationship tables

Plural.

Examples

```
collection_items

discussion_likes

user_badges
```

Domain prefixes should be used whenever ambiguity exists.

Examples

```
book_likes

book_comments

discussion_comments

user_preferences
```

Avoid generic names.

Examples

```
likes

comments

settings
```

---

# Primary Keys

Every table uses:

```
uuid
```

as its primary key.

Generated by PostgreSQL.

---

# Foreign Keys

Always enforce relationships through foreign keys.

Example

```
reading_progress

↓

books

↓

profiles
```

Avoid orphan records.

---

# Referential Integrity

Use:

```
ON DELETE CASCADE
```

only when child records have no meaning without the parent.

Use:

```
RESTRICT
```

when accidental deletion would cause data loss.

---

# Row-Level Security

Every public table must enable RLS.

Requirements

- SELECT policy
- INSERT policy
- UPDATE policy
- DELETE policy

Policies should use

```
auth.uid()
```

rather than client-provided identifiers.

---

# Authorization Model

Authorization is layered.

```
Frontend

↓

Server Action

↓

Repository

↓

Row-Level Security
```

The database is the final authority.

---

# Migrations

All schema changes use versioned SQL migrations.

Never modify production schemas manually.

Migration requirements:

- transactional
- reversible when practical
- reviewed
- tested in staging

---

# Indexing

Create indexes for:

- foreign keys
- frequently filtered columns
- sorting columns
- search columns

Avoid unnecessary indexes on write-heavy tables.

---

# Constraints

Prefer database constraints over application checks.

Examples

```
UNIQUE

CHECK

FOREIGN KEY

NOT NULL
```

Business invariants should be enforced as close to the data as possible.

---

# Views

Views may be used for read models.

Requirements

- read-only
- well documented
- avoid business logic

---

# Functions

Database functions should be limited to:

- utilities
- computed values
- triggers
- maintenance

Business workflows belong in the application.

---

# Triggers

Triggers should remain minimal.

Examples

- updated_at timestamps
- audit logging
- queue insertion

Avoid complex business logic inside triggers.

---

# Storage

Supabase Storage contains:

- avatars
- book covers
- uploaded books
- attachments

The database stores only references.

---

# Transactions

Use transactions whenever multiple tables must remain consistent.

Examples

- collection creation
- reading progress updates
- achievement unlocking

---

# Pagination

All list queries should be paginated.

Never fetch entire tables.

Preferred ordering:

```
created_at DESC
```

or

```
updated_at DESC
```

---

# Soft Deletes

Default strategy:

Hard delete.

Use soft deletes only when recovery or auditing is required.

Avoid unnecessary `deleted_at` columns.

---

# Auditing

Record important events.

Examples

- profile updates
- reading milestones
- security events

Audit tables should be append-only.

---

# Performance

Prioritize

- indexes
- query plans
- pagination
- selective columns
- batched operations

Avoid

- SELECT *
- N+1 queries
- unnecessary joins

---

# Schema Evolution

Breaking changes require:

1. Migration.
2. Application compatibility.
3. Verification.
4. Cleanup.

Prefer additive migrations before destructive ones.

---

# Backups

Production requirements:

- automated backups
- point-in-time recovery
- staging validation before destructive migrations

Never execute destructive migrations without verified backups.

---

# Type Generation

Database types are generated from the schema.

The generated types are the source of truth.

Do not manually edit generated database types.

---

# Database Review Checklist

Before merging a schema change, verify:

- Does the table belong to the correct domain?
- Is the name explicit?
- Are foreign keys defined?
- Is RLS enabled?
- Are policies correct?
- Are indexes sufficient?
- Is the migration transactional?
- Is referential integrity preserved?
- Are generated TypeScript types updated?
- Has the migration been tested on staging?
